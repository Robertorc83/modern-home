# Demo video script (5 minutes)

Record at 1440p or 1080p, browser at 1440×900, two browser windows side by side for the live scenes
(agent on the left, buyer on the right), and a terminal for the MCP scene. Start with
`docker compose up` already healthy and a fresh seed (`docker compose down -v && docker compose up --build`).

Have these open before recording: `http://localhost:3000/login`, a second browser profile or incognito
window on the same URL, a terminal in the repo, and `http://localhost:4566/_aws/ses` in a tab.

| Time | Scene | What to show | What to say |
|---|---|---|---|
| 0:00–0:30 | **The problem and how I read the brief** | The login page. | "Two sided scheduling: sellers publish *when* a house can be shown; buyers say *when they're free* and get only the listings that fit. The brief is ambiguous on purpose, so I made three calls: a tenant is a brokerage, with agents on the seller side and buyers on the other; time zones are first class because a buyer in Toronto books a house in Denver; and no double booking is enforced by the database, not by the app." |
| 0:30–1:15 | **Seller flow** | Click **Agent · Acme Realty**. Open *My listings*, open **1420 Larimer St #5B**. Scroll the weekly window grid: Saturday 9–12, slot 30 min, buffer 15, lead time 12 h, blackout dates (empty; add one to show the chip), auto confirm off. Change Saturday to end at 1:00 PM, **Save changes**, point at the slot preview: a 12:00 PM Saturday slot appears (the grid steps by slot + buffer = 45 min). | "Rules are wall clock times in the listing's zone. Slot length plus buffer defines a fixed grid, which is what later lets the database guarantee uniqueness. Lead time and horizon bound the window; blackouts remove a day." |
| 1:15–2:15 | **Buyer flow with AI** | Second window: **Buyer · Acme Realty**. Tab *Describe it*, type `weekday evenings after 6 except Thursday, Saturday morning`, click **Parse**. Show the parsed windows, the summary and the dated ranges for review, and the provider badge ("Rule-based (no API key)" or "Claude Haiku"). Set **Near** to `LoDo` (the radius select enables once Near is filled), radius 10 km, click **Search with these**. Show cards sorted by distance ("0.5 km away") with slot chips grouped by day. Switch **Your time zone** to America/Toronto, then **Parse** and **Search with these** again: the chips now show Toronto time with the "MST local" time under each. | "The sentence is parsed into structured windows, either by Claude Haiku with a strict schema or by a deterministic parser when there is no key. Either way the buyer reviews it before searching. Matching intersects the buyer's ranges, in their zone, with each listing's open slots. Near uses a 2dsphere index and `$geoNear`, so cards carry a distance." |
| 2:15–2:50 | **Double booking guarantee** | Click the Saturday **9:45** chip on Larimer (leave 9:00 free for the closing scene). Show "Held for you for 5:00" counting down (the TTL hold). In the terminal run the concurrency test: `dotnet test tests/Api.IntegrationTests --filter Twenty_parallel` (pre-run it once so it's fast) or show `docs/adr/002-mongodb.md` with the index. Click **Confirm booking**: toast "Showing requested". | "While the dialog is open the slot is held in a TTL collection; Mongo expires it itself. Booking is an insert under a unique partial index on the slot key plus one claim per five minute bucket, so twenty concurrent requests for one slot give one 201 and nineteen 409s, and a slot can't overlap another even after the agent changes the slot length." |
| 2:50–3:15 | **Tenant isolation** | Sign in as **Buyer · Northstar Homes** in the second window: only Toronto listings. Paste an Acme listing URL (`/buyer/listings/<id>`): "This listing was not found in your brokerage" (the API answered 404, not 403). | "Tenant comes from the token, never the body. Every repository adds it to every filter, so another brokerage's id simply doesn't exist: 404, not 403. The tests cover reads, writes, lists, geo and the admin screens." |
| 3:15–3:45 | **Architecture and trade offs** | `docs/architecture.md` mermaid diagram; `docs/adr/` list. Mention `docs/aws-deployment.md`, then open the admin **Outbox and emails** page (Admin · Acme Realty) and its "Open the LocalStack SES inbox" link (`/_aws/ses`) showing the "New showing request" email from the scene 4 booking (delivered within seconds). | "Modular monolith: modules as projects, in process domain events, no MediatR. MongoDB earned its place: documents with per type attributes, geo, change streams, TTL holds, the unique partial index. The honest trade off: free form durations would push bookings to Postgres with an exclusion constraint, and the repository boundary keeps that change contained. Notifications go outbox → SQS → worker → SES, here on LocalStack; the AWS doc is the production target." |
| 3:45–4:05 | **How I used Claude Code** | The repo tree, `tests/`, and the brief. | "Spec first: the brief became a contract and a phase plan; Claude Code built against it while tests guarded the core: DST transitions, a Toronto buyer on a Denver listing, isolation, the 20 way booking race, and the MCP server driven by the official client." |
| 4:05–4:50 | **Closing scene: book from Claude Code** | Buyer window: *AI assistant* page, create a token, copy the `claude mcp add` command, run it in the terminal. Then `claude` and prompt: **"Find me a Saturday morning showing in Denver under 600k and book it."** Approve the `book_showing` tool call. Agent window (left) on *Inbox*: the new request appears without a refresh, with the amber highlight and the toast "New showing request · Bea Martin · 1420 Larimer St #5B". Click **Approve**; the buyer's *My showings* flips to Confirmed live with the toast "Showing confirmed". | "The scheduler is also an MCP server inside the same monolith, on the same application services, with personal access tokens scoped to the user's tenant and role. Read tools are marked read only; booking isn't, so Claude asks first. The booking lands in the agent's inbox through a MongoDB change stream over Server Sent Events." |
| 4:50–5:00 | **Next steps** | README "Next steps". | "Next: Atlas Vector Search for semantic listing search, calendar sync for agents, and a CDK stack for the AWS design. Thanks." |

## Before recording

* `docker compose down -v && docker compose up --build` and wait for `web` to be healthy; the seed runs by itself.
* Run `dotnet test` once so the concurrency test is warm if you plan to show it live.
* `claude mcp remove showings` if a previous registration exists; the AI assistant page gives the fresh command.
* Keep the Saturday 9:00 LoDo slot free for the MCP scene (the seed books 11:15 only; scene 4 uses 9:45). Claude
  tends to pick the earliest open slot; if it picks another, that is fine, the inbox shows it the same way.
* If `ANTHROPIC_API_KEY` is in `.env`, the parser badge says Claude Haiku; without it, Rule-based. Both parse the demo
  sentence identically.
